# Семантичний пошук наукових статей arXiv

## Опис проєкту

У цій домашній роботі я створила систему семантичного пошуку наукових статей із датасету arXiv.

Основна ідея такого пошуку - знаходити статті не тільки за конкретними словами, а й за змістом запиту. Наприклад, користувач може описати тему своїми словами, а система має знайти наукові роботи, які найбільше їй відповідають.

Для цього я використала модель SPECTER2, яка перетворює тексти на числові вектори, та векторну базу даних Pinecone, де ці вектори зберігаються.

Під час роботи я також перевірила пошук із фільтрами, порівняла метрики схожості та дослідила, як розбиття тексту на менші частини впливає на результати.

Ця модель спеціально розроблена для роботи з науковими текстами, тому я вирішила, що вона добре підходить для мого завдання.

### Чому я вибрала SPECTER2, а не MiniLM?

MiniLM - це компактна та швидка модель, яка підходить для багатьох загальних завдань семантичного пошуку.

Але в моєму випадку потрібно було працювати саме з науковими статтями.

SPECTER2 навчена представляти наукові документи у вигляді векторів, тому я вибрала її як більш спеціалізований варіант.

Недоліком SPECTER2 є те, що вона потребує більше ресурсів і працює повільніше, особливо на CPU.

У моєму випадку це було помітно під час створення ембеддингів для 8000 статей.

## 5. Порівняння метрик схожості

Скрипт: `scripts/06_compare_metrics.py`

У цій частині я порівняла три метрики:

- Cosine similarity
- Dot Product
- Euclidean Distance (L2)

Для експерименту використала нормалізовані ембеддинги та порівняла результати пошуку.

Отримала такі значення для одного з найближчих результатів:

| Метрика | Значення |
|---|---:|
| Cosine similarity | 0.895140 |
| Dot Product | 0.895139 |
| Euclidean Distance (L2) | 0.457953 |

Усі три метрики дали однакові топ-5 результатів.

### Чому Cosine та Dot Product майже однакові?

Cosine similarity порівнює напрямки векторів, а Dot Product також враховує їхню довжину.

Але якщо вектори нормалізовані до одиничної довжини, Dot Product стає рівним Cosine similarity.

Саме тому в моєму експерименті результати практично збіглися.

Невелика різниця в числах пов'язана з точністю обчислень.

### Чому L2 теж дала ті самі результати?

Для нормалізованих векторів евклідова відстань пов'язана з косинусною схожістю:

`L2² = 2 - 2 × cosine_similarity`

Тобто чим більша косинусна схожість, тим менша евклідова відстань.

Через це порядок найближчих векторів для нормалізованих даних буде однаковим.

### Яку метрику я вибрала?

Для основного пошуку я використала cosine similarity.

На мою думку, вона добре підходить для порівняння текстів, тому що дозволяє оцінювати схожість їхнього змісту без залежності від довжини вектора.

Результати експерименту збережені у файлі `data/metrics_comparison.csv`.

## 6. Порівняння стратегій chunking

Скрипт: `scripts/05_chunking.py`

У цій частині я перевірила, як розбиття тексту на менші фрагменти впливає на семантичний пошук.

Для експерименту вибрала 30 статей із найдовшими анотаціями.

Середня довжина анотації становила 1945 символів.

Я порівняла дві стратегії.

**Fixed-size chunking**

Текст розбивається на фрагменти приблизно по 100 слів. Між сусідніми фрагментами є перекриття 20 слів.

Перекриття потрібне, щоб важлива інформація не губилася на межі двох чанків.

**Sentence-based chunking**

Текст розбивається за межами речень, після чого речення об'єднуються у фрагменти приблизно по 100 слів.

Перевага такого підходу в тому, що речення не розриваються посередині.

Цю стратегію я назвала `chunks-semantic`, хоча фактично вона базується на межах речень, а не на окремій моделі для визначення смислових блоків.

### Кількість створених чанків

| Стратегія | Кількість чанків |
|---|---:|
| Fixed-size | 116 |
| Sentence-based | 112 |

Для кожного чанка я створила окремий ембеддинг за допомогою SPECTER2.

Після цього завантажила всі чанки в Pinecone.

### Використання namespaces

Спочатку я планувала створити окремі індекси для двох стратегій.

Але в безкоштовному тарифі Pinecone Starter доступний тільки один індекс.

Тому я використала два окремі namespaces всередині існуючого індексу:

- `chunks-fixed`
- `chunks-semantic`

Початкові 8000 статей залишилися у стандартному namespace.

У результаті Pinecone містила:

- 8000 векторів початкових статей;
- 116 векторів fixed-size чанків;
- 112 векторів sentence-based чанків.

**Загалом - 8228 векторів у трьох namespaces.**

Це дозволило порівняти стратегії без створення додаткових індексів.

### Результати пошуку

Я перевірила три запити:

1. `machine learning methods for image classification`
2. `black holes and gravitational waves`
3. `quantum computing and quantum information`

Для кожного запиту отримала топ-5 результатів в обох namespaces.

Найвищі показники similarity:

| Запит | Fixed-size | Sentence-based |
|---|---:|---:|
| Image classification | 0.8281 | 0.8409 |
| Black holes | 0.8252 | 0.8158 |
| Quantum computing | 0.8429 | 0.8387 |

Для першого запиту вищий показник отримала стратегія sentence-based.

Для двох інших трохи вищі значення були у fixed-size.

Але ці цифри не означають, що одна стратегія завжди краща.

Similarity показує, наскільки близькими є вектори, але не гарантує, що знайдена стаття справді відповідає запиту.

### Що я помітила під час експерименту?

Для запиту про класифікацію зображень система знаходила статті про нейронні мережі, медичну сегментацію та реконструкцію зображень.

Ці результати були досить близькими до теми.

А от для запиту про чорні діри серед результатів були статті з інших напрямів математики та машинного навчання.

Це показало мені, що навіть високий similarity score не завжди означає хорошу релевантність.

Також потрібно враховувати, що для цього експерименту я використала тільки 30 статей із найдовшими анотаціями. У такій маленькій вибірці може просто не бути статей, які добре відповідають конкретному запиту.

### Яка стратегія краща?

За результатами мого невеликого експерименту не можна однозначно вибрати переможця.

Fixed-size простіша в реалізації та дозволяє контролювати розмір фрагментів.

Sentence-based краще зберігає цілісність речень, тому текст чанків зазвичай легше читати.

Для наукових анотацій я б частіше використовувала розбиття за реченнями, але для остаточного вибору потрібно протестувати більше запитів і вручну оцінити релевантність результатів.

Результати збережені у файлі `data/chunking_results.csv`.

## 7. Теоретичні питання та аналіз

### 7.1. Чим семантичний пошук відрізняється від лексичного?

Лексичний пошук, наприклад BM25 або TF-IDF, орієнтується переважно на слова, які зустрічаються в запиті та документах.

Це добре працює, якщо користувач знає точні терміни.

Але якщо однакову ідею описати різними словами, лексичний пошук може пропустити потрібний документ.

Семантичний пошук використовує ембеддинги та порівнює зміст текстів.

Наприклад, запит про розпізнавання об'єктів на зображеннях може знайти статті про computer vision, навіть якщо формулювання не збігаються дослівно.

При цьому лексичний пошук теж має свої переваги. Він може бути точнішим, коли потрібно знайти конкретну назву, формулу, ідентифікатор або спеціальний термін.

Тому в реальних системах часто є сенс комбінувати обидва підходи.

### 7.2. Що буде, якщо зробити дуже маленькі чанки?

Якщо розбивати текст на фрагменти по 10–15 слів, можна втратити важливий контекст.

Наприклад, у першому чанку буде опис проблеми, а в наступному - пояснення методу її вирішення.

Окремо ці фрагменти можуть не передавати повний зміст.

Також маленькі чанки збільшують кількість векторів, які потрібно створити та зберігати.

Це впливає на витрати ресурсів.

### 7.3. Що буде, якщо зробити дуже великі чанки?

Якщо використовувати фрагменти по 500 і більше слів, у них може бути одразу кілька різних тем.

Тоді один ембеддинг представлятиме великий обсяг інформації, і конкретна важлива деталь може загубитися.

Крім того, потрібно враховувати обмеження моделі за кількістю токенів.

У моєму коді використовується `max_length=512`, тому надто довгі тексти можуть обрізатися під час токенізації.

На мою думку, оптимальний розмір чанка залежить від типу тексту та завдання. Його краще підбирати експериментально.

### 7.4. Навіщо потрібне перекриття чанків?

Перекриття допомагає зберігати контекст між сусідніми фрагментами.

Наприклад, якщо важливе пояснення починається в кінці одного чанка та продовжується в наступному, без перекриття частина змісту може загубитися.

У своєму експерименті для fixed-size я використала перекриття 20 слів.

Але занадто велике перекриття теж має недоліки, оскільки збільшує кількість повторюваного тексту та витрати на зберігання.

### 7.5. Чому Cosine та Dot Product дають однаковий результат після нормалізації?

Cosine similarity обчислюється як скалярний добуток, поділений на добуток довжин двох векторів.

Якщо обидва вектори мають довжину 1, знаменник дорівнює 1.

Тому cosine similarity стає рівною звичайному скалярному добутку.

Саме це я побачила у своєму експерименті.

### 7.6. Які обмеження Pinecone Starter я помітила?

Під час роботи я зіткнулася з обмеженням кількості індексів.

Мій тариф дозволяв створити тільки один індекс, тому для експерименту з chunking довелося використовувати namespaces.

Для навчального проєкту цього було достатньо.

Але якщо потрібно працювати з різними конфігураціями індексів або значно більшими обсягами даних, доведеться враховувати тарифні обмеження.

### 7.7. Як можна масштабувати систему до 10 мільйонів статей?

Якби потрібно було працювати не з 8000, а з 10 мільйонами статей, я б змінила підхід до обробки даних.

По-перше, створювала б ембеддинги пакетами та використовувала GPU або іншу обчислювальну інфраструктуру.

По-друге, не зберігала б усі дані в оперативній пам'яті одночасно.

По-третє, завантажувала б вектори в Pinecone частинами.

Також потрібно було б продумати фільтрацію, оновлення індексу, вартість зберігання та кількість пошукових запитів.

Для такої системи важливо оцінювати не тільки якість пошуку, а й швидкість, стабільність та витрати.

Тому для оцінювання якості пошуку важливо дивитися не тільки на similarity score, а й на сам зміст знайдених статей.

## 8. Висновки

Під час виконання цієї домашньої роботи я навчилася працювати з векторною базою даних Pinecone та створювати систему семантичного пошуку.

Спочатку я підготувала датасет із 8000 наукових статей, потім створила ембеддинги за допомогою SPECTER2 і завантажила їх у Pinecone.

Після цього перевірила пошук із фільтрами за роком і категорією.

Також порівняла cosine similarity, dot product та евклідову відстань. На практиці побачила, чому після нормалізації векторів ці метрики можуть давати однаковий порядок результатів.

Окремо мені було цікаво перевірити chunking.

Я порівняла розбиття тексту за кількістю слів і за реченнями та побачила, що результати можуть відрізнятися навіть для однакових запитів.

Ще один важливий висновок - високий similarity score не завжди означає, що знайдена стаття справді релевантна.

Загалом мені вдалося створити працюючу систему семантичного пошуку та перевірити основні можливості векторної бази даних на практиці.

## 9. Як запустити проєкт

### 9.1. Встановлення

Для запуску потрібен Python 3.11.

Спочатку потрібно клонувати репозиторій та перейти в папку проєкту.

Створити віртуальне середовище:

```powershell
python -m venv .venv
```

Активувати його в Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Встановити залежності:

```powershell
pip install -r requirements.txt
```

### 9.2. Налаштування Pinecone

У кореневій папці потрібно створити файл `.env`:

```env
PINECONE_API_KEY=your_api_key
PINECONE_INDEX=arxiv-semantic-search
```

Замість `your_api_key` потрібно вказати власний API-ключ Pinecone.

### 9.3. Підготовка датасету

Завантажити датасет arXiv із Kaggle:

https://www.kaggle.com/datasets/Cornell-University/arxiv

Помістити файл `arxiv-metadata-oai-snapshot.json` у папку `data`.

### 9.4. Запуск скриптів

Підготовка даних:

```powershell
python scripts/01_prepare_data.py
```

Створення ембеддингів:

```powershell
python scripts/02_embed.py
```

Завантаження в Pinecone:

```powershell
python scripts/03_load_to_pinecone.py
```

Семантичний пошук:

```powershell
python scripts/04_search.py
```

Порівняння метрик:

```powershell
python scripts/06_compare_metrics.py
```

Експеримент із chunking:

```powershell
python scripts/05_chunking.py
```
